# Telegram Pipeline Requirements

## 1) 기능 요구사항 (Functional)

### R1. 채널 메시지 수집
- 등록된 텔레그램 채널 목록에서 신규 메시지를 주기적으로 수집한다.
- 텍스트 기반 메시지만 처리하며, 미디어 전용 메시지는 무시한다.
- 수집 대상 채널 목록 및 인증 정보는 환경 변수로 관리하고 코드 하드코딩을 금지한다.
  구체적인 키 이름·권한 부여 절차는 운영 매뉴얼에서 관리한다.

### R2. 메시지 정규화
- 비정형 텍스트에서 발신 채널, 시각, 핵심 텍스트, 추출 키워드를 분리하여
  정규화된 딕셔너리(`telegram_message_dict`)로 변환한다.
- 정규화 실패 메시지는 결과 리스트에서 제외(스킵)하고 로그만 남긴다.

### R3. 책임 한정 (관심사 분리)
- 본 파이프라인은 수집/정제 + 반환까지만 담당한다.
- Market Chronicles 인덱스 적재, AI 프롬프트 주입 등 후속 동작은 본 파이프라인이
  직접 호출하지 않는다(오케스트레이터가 위임 라우팅).
- `src/memory/`, `src/strategy/` 등 후속 도메인 모듈을 import 하지 않는다.

### R4. 중복 방지
- 채널별 마지막 처리 메시지 식별자를 영속화하여 시스템 재기동 후에도
  중복 수집을 방지한다(영속화 키 구조는 03 상태로직 참조).

## 2) 비기능 요구사항 (Non-Functional)

### N1. 에러 격리 (A-Type 기본)
- Rate Limit / 네트워크 일시 장애 / 단일 메시지 파싱 실패는 A-Type 으로 처리.
- 외부 장애로 인해 트레이딩 코어(KIS 주문, 리스크 감시) 흐름이 중단되어서는 안 된다.
- 본 파이프라인은 어떠한 예외도 호출자에게 전파하지 않으며, 항상 결과 리스트를 반환한다.

### N2. 운영자 개입 신호 (B-Type 위임)
- 인증 정보 누락/잘못 구성 등 자가복구 불가 케이스는 오케스트레이터가 B-Type 으로
  처리하도록 신호(예: 결과 dict 의 메타 필드)만 노출한다. Pause 결정 자체는 본
  파이프라인이 내리지 않는다.

### N3. 토큰 효율
- 정제 결과의 핵심 텍스트는 후속 AI 호출 비용을 고려하여 길이 상한을 둔다.
- 원문 보존이 필요한 경우 보조 필드에 분리 저장한다.

## 3) 운영 제약
- 텔레그램 인증 정보 및 채널 목록은 환경 변수로만 주입(.env 직접 읽기 금지).
- 외부 도메인(Market Chronicles 등)으로의 직접 import 금지.
- 폴링 주기, 메시지 최대 길이, 채널별 last_id 영속화 경로는 본 기능 사양 문서에서
  관리한다(아키텍처 문서에는 운영 정책만 명시).
